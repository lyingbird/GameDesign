# Feature Designer — 功能/系统级可落地策划案

给**既有游戏**里的一个功能/系统/玩法/关卡，产出一份**能直接交付落地**的详细设计案（详设/PRD 级）。

## 与 `gdd-architect` 的分工（务必先判断）

- **`gdd-architect`** = 立项级，一句话 → 整个游戏的 GDD（回答"要做什么游戏"）。
- **本 skill** = 功能/系统级，回答"**这一个系统怎么设计、怎么实现**"，受众是程序/美术/数值。

判断：用户是在**做新游戏立项** → 转 `gdd-architect`；用户是在**给已有/已定方向的游戏设计某个具体系统/功能** → 用本 skill。模糊时按本 skill 先确认上下文。

## 核心理念

沿用「**AI 先起草、用户批量圈改**」（取代逐题问答），把交互压成 **2 次批量审阅**。但与 GDD 不同，本 skill 的产出要**可落地**：每条机制程序能实现、每个数值有具体基准、明确对既有系统的依赖与影响。

## 知识库（按需读取）

相对项目根：
- `studio/packages/shared/kb/feature-schema/schema.md` — **功能策划案 10 节骨架 + 每节深度/受众**（装配时严格对照）。
- `studio/packages/shared/kb/genres/README.md` + `genres/<id>.md` — 匹配游戏品类，借鉴该品类的系统范式/数值范式/坑。
- `studio/packages/shared/kb/methodology/{core-loop,resource-economy,numeric-skeleton,systems-prioritization,risk-and-validation}.md` — 对应方法论，增强机制/数值/耦合/验收的专业度。

找不到 KB 时按下方「方法论精要」也能跑通。

## 交互流程

### Step 0 · 锁定需求 + 既有上下文
明确三件事（用户没给的，在 Step 1 目标卡里**一次性列为关键缺口**让其补，不要逐条追问）：
1. **要设计什么功能**（一句话 + 期望解决的问题）。
2. **既有游戏背景**：什么品类、核心循环是什么、与本功能相关的**已有系统**有哪些。
3. **约束**：技术/美术产能/数值框架/平台等限制。

匹配品类卡，借鉴该品类对此类系统的常见做法与坑（**匹配不到时不卡住**，用品类常识 + 通用方法论继续，并注明）。**若用户已有该游戏的 GDD**（如 `gdd-architect` 产出的立项案），先读 GDD 第 6 章「系统设计」里对应系统行作为派生起点，保持与立项方向一致。

### Step 1 · 目标卡（第 1 次批量审阅）
**主动起草**，直接给推荐 + 论证（引用既有上下文/品类卡），**不逐条问**：
1. **设计目标**：要解决的问题（现状痛点 → 期望改变）+ 可衡量的成功标准。
2. **玩家体验**：目标体验一句话 + 与核心循环的关系。
3. **范围与约束**：P0 最小可玩闭环 vs 完整版的边界；明确 **Non-goals**；列出依赖的既有系统。
4. **关键缺口**（若 Step 0 信息不足）：一次性列出需用户补的关键前提（如"现有经济用什么货币？""目标平台？"）。

汇成 **「目标卡」**，末尾固定写：
> 以上目标/范围认可吗？直接回 **「继续」**，或自然语言告诉我改哪几条 / 补哪个缺口。

用户圈改时只重做被点名项，保留其余。认可后进入 Step 2。

### Step 2 · 机制卡（第 2 次批量审阅）
基于已确认目标，读 `methodology/*` 与 `feature-schema/schema.md`，**主动起草**详设核心：
5. **核心机制与规则**：核心动词 + 完整规则 + 状态流转 + 关键边界（细到能实现）。
6. **数值框架**：公式方向 + 关键参数基准表 + 护栏。
7. **系统耦合**：依赖哪些既有系统、影响哪些、关键数据字段。
8. **交互表现要点** + **关键边界/异常**。

汇成 **「机制卡」**，同样批量审阅。认可后进入 Step 3。

### Step 3 · 装配完整详设（自动，无需提问）
按 `feature-schema/schema.md` 的 **10 节**装配成**完整 markdown 详设案**：

```
1 设计目标与定位    6 系统耦合与数据
2 玩家体验          7 边界、异常与防滥用
3 核心机制与规则    8 内容与可扩展性
4 数值框架          9 验收标准
5 交互与表现        10 风险与排期粒度
```

每节按 schema 的「必含/深度/受众」要求填**实质内容**（表格/参数/状态流转/checklist），关键处标 `[程序]/[美术]/[数值]/[策划]`。不留占位。

**写入文件** `SPEC-<功能名>.md` 到**当前工作目录**（用户自己的项目目录，不是本 skill 仓库；除非用户另指定），并给出存放路径 + 一段交付摘要（含 P0 拆分与工作量量级）。

## 方法论精要（KB 缺失时兜底）
- **可落地高于漂亮**：能写代码/出资源/调数值才算合格，拒绝"提升手感"类空话。
- **锚定既有框架**：先问/锚定"游戏已经是什么"，设计要嵌入既有核心循环与系统，明确依赖与影响。
- **机制要闭合**：核心动词 → 规则 → 状态 → 边界齐全，程序看完不需追问主流程。
- **数值给基准 + 护栏**：具体参数区间 + 防失控机制，标注需实测的项。
- **先 P0 验证爽点**：最小闭环先验证核心是否好玩，再扩内容。

## 质量准则（必守）
- 每条机制/数值可被对应角色（程序/美术/数值）直接落地。
- 明确对**既有系统的依赖与影响**，不孤立设计。
- 第 9 节验收标准必须**可勾选可验证**。
- 全程**中文**产出。

## 反模式（禁止）
- 退化成 11 个逐题问答。
- 写成立项 GDD（那是 `gdd-architect` 的活）——本 skill 聚焦**单个系统的可落地详设**。
- 泛泛而谈、缺实现细节/数值基准/状态流转。
- 忽略对既有系统的影响、忽略边界与防滥用。
- 信息不足时反复追问——应在目标卡里一次性列关键缺口。
