# 功能/系统策划案 Schema（Feature Spec · 10 节）

> 这是 `feature-designer` skill 的**权威详设模板**。与 GDD（立项级、回答"做什么游戏"）不同，
> Feature Spec 是**功能/系统级**的可落地详细设计案，回答"**这一个系统怎么设计、怎么实现**"，
> 受众是程序 / 美术 / 数值，要求细到**照着能写代码、能出资源、能调数值**。
>
> 与 GDD 的边界：GDD 第 6 章"系统设计"只列**有哪些系统 + 优先级**；本 Spec 是把**其中一个系统**
> 展开成完整详设。一份 GDD 可派生多份 Feature Spec。
>
> ### 全局风格约定（所有节遵守）
> - **可落地优先**：每条机制要可被程序实现、可被美术理解、可被数值调参；避免"提升体验""优化手感"这类空话。
> - **既有上下文锚定**：始终基于"这个游戏已经是什么"来设计，明确**依赖**与**影响**的既有系统。
> - **表格/状态图密集**：规则用表格，流程用状态/时序描述，数值用参数表。
> - **标注受众**：关键处标 `[程序]` / `[美术]` / `[数值]` / `[策划]`，让对应角色快速定位。

---

## 1. 设计目标与定位
**受众**：全体 · **必含**：
- **要解决的问题**：这个功能补什么体验缺口 / 满足什么需求（1~3 条，每条说清"现状痛点 → 期望改变"）。
- **在既有游戏中的位置**：属于哪个系统层（战斗/养成/经济/社交/外围…），与核心循环的关系一句话。
- **成功标准**：可衡量的目标（如"提升 X 留存""给 build 增加 N 种新组合""新增 1 个长线追求"），尽量可验证。
- **明确不做（Non-goals）**：划定边界，防 scope 膨胀。

## 2. 玩家体验
**受众**：策划/美术 · **必含**：
- **目标体验一句话**：玩家用这个功能时**应该感受到什么**。
- **体验流程**：玩家从接触→使用→获得反馈→形成追求的完整路径（3~6 步）。
- **情感/动机曲线**：什么时刻爽、什么时刻有取舍张力、长线动机是什么。
- **目标玩家**：哪类玩家最受益（呼应游戏既有画像）。

## 3. 核心机制与规则（详设心脏）
**受众**：程序/策划 · **必含**：
- **核心动词与规则**：玩家具体能做什么操作，每个操作的**完整规则**（前置条件 → 行为 → 结果）。
- **状态与流转**：对象/系统的状态枚举 + 状态间的转移条件（用"状态：触发条件 → 目标状态"列表或表格表达）。
- **关键流程**：核心交互的步骤化描述（可用时序：玩家操作 → 系统响应 → 反馈）。
- **规则边界**：上限/下限/冷却/堆叠规则/优先级/冲突裁决（用表格列全）。
- 要细到**程序能据此实现，不需再追问主流程**。

## 4. 数值框架
**受众**：数值 · **必含**：
- **公式方向**：核心公式（乘法+衰减优先），标出每个乘区/加区的来源。
- **参数表**：关键参数的**具体基准值或区间**（用表格：参数 | 基准值 | 范围 | 说明）。
- **平衡基准**：成长/产出/消耗曲线形状 + 关键锚点数值（量级，非死数）。
- **护栏**：防数值失控的封顶/独立乘区/递减/保底机制。
- 标注哪些需后续**模拟/实测**校准（可接 `numeric-audit`）。

## 5. 交互与表现
**受众**：美术/前端 · **必含**：
- **UI 元素清单**：需要哪些界面/控件/图标/信息展示（列表）。
- **操作流程**：玩家从入口到完成的点击/操作路径。
- **反馈设计**：视觉/音效/震动/数字弹跳等即时反馈，强调"每个操作都有可感知回应"。
- **信息层级**：哪些信息常驻、哪些按需展开，避免信息过载。
- **可访问性**：避免纯颜色编码（色盲玩家盲区）——关键信息用形状/图标/文字辅助区分，不只靠颜色。
- **本地化**：列出涉及的可见文本（名称/提示语/数字格式），标为需本地化项。
- 给前端/美术的接口级描述（状态如何映射到表现）。

## 6. 系统耦合与数据
**受众**：程序 · **必含**：
- **依赖**：本功能依赖哪些既有系统/数据（读什么）。
- **影响**：本功能改变/写入哪些既有系统/数据（写什么），是否影响既有平衡。
- **数据结构**：核心数据字段 / 配置表结构 / 存档结构（关键字段列表）。
- **数据流**：一次完整使用涉及的数据读写时序（简述）。
- **埋点/数据采集** `[程序][数据]`：列出关键埋点事件（如 `feature_used` / 关键状态变更）+ 上报字段，**且必须能采集到 §1 成功标准与 §9 验收所需的指标**——成功标准不能悬空在"无数据来源"上。

## 7. 边界、异常与防滥用
**受众**：程序/数值 · **必含**：
- **极端 case**：最小/最大/零/负/并发/断线重连等边界输入的处理。
- **容错**：非法操作、状态不一致、配置缺失时的降级/兜底。
- **防滥用**：防刷 / 防卡数值 / 防破坏平衡的护栏（呼应 §4）。

## 8. 内容与可扩展性
**受众**：策划/程序 · **必含**：
- **首版内容量**：MVP 需要多少内容单元（如"8 个附魔词条""3 个阶段"），明确数量。
- **配置化**：哪些走配置表（策划可调）、哪些写死。
- **扩展挂点**：未来加内容/加类型时的预留接口，避免一次做全。

## 9. 验收标准
**受众**：全体 · **必含**：可测的**完成定义（Definition of Done）**，分维度列 checklist：
- 功能维度：核心规则是否都实现且可用。
- 数值维度：关键基准是否达标 / 经济是否闭环 / 无失控组合。
- 体验维度：目标体验是否达成（可用主观评测或埋点指标，呼应 §6 埋点）。
- **测试要点**：把 §7 的每个边界/异常 case 映射成可执行的测试断言（边界测试矩阵）——checklist 必须覆盖 §7 列出的每个异常分支。
- 每条尽量**可勾选、可验证**。

## 10. 风险与排期粒度
**受众**：全体/制作人 · **必含**：
- **风险表**：高/中/低 + 风险点 + 缓解方案（重点：数值失控 / 与既有系统冲突 / 工作量超预期 / 体验不达预期）。
- **实现拆分**：P0（最小可玩闭环，先验证核心爽点）/ P1 / P2，每档列清做什么。
- **工作量量级**：粗粒度估（人天量级或 S/M/L），帮制作人排期。
