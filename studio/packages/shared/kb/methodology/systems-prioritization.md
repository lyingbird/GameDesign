# 系统优先级：P0/P1/P2 分级与 MVP 闭合

## 核心概念

systems_resources 节点要回答"**有哪些系统、它们怎么连**"。光列系统不够，必须**给每个系统标优先级**，决定开发顺序和首版投入。标准做法采用 P0/P1/P2 三级（每个系统一份说明书：目标 / 核心机制 / 与主循环关系 / 优先级）。

**三级定义**：
- **P0（核心，必须最先验证）**：构成核心正反馈链、缺了循环就不闭合的系统。**最早完成并进入原型验证**。以《典藏图书馆》为例，P0 有：研读派遣（资源主入口）、禁书研究（差异化核心）、离线收益（挂机体验，"必须从原型期接入否则无法验证挂机"）。
  - 判据：在核心循环句里直接出现；砍掉它循环断裂。
- **P1（支撑，首版必须包含）**：扩展主循环、提供成长骨架，但可在 P0 验证后补。例如：馆区修复（"核心循环验证后补充，但首版必须包含"）、技能成长（"与馆区共同扩展主循环"）。
- **P2（增益，首版轻量）**：增加深度/构筑空间，首版克制实现、不应完全砍掉。例如：装备构筑（"首版轻量实现，不应完全砍掉，对应全部三层"）。

**每个系统的说明书结构**（产出 schema）：
1. **目标**：它在整体里承担什么职责（一句话）。
2. **核心机制**：玩家在它里面做什么、产出/消耗什么、关键参数有哪些。
3. **MVP 规则/克制量**：首版具体做多少（数量上限、档数、节点数），呼应 scope-discipline。
4. **与主循环关系**：它的产出流向谁、消耗谁、如何反哺核心循环——这是判断优先级的依据。
5. **优先级**：P0/P1/P2 + 一句理由。

**MVP 闭合（MVP closure）**：所有 P0 系统连起来，必须能跑通**完整核心正反馈链一整圈**。检验法：把 P1/P2 全部暂时移除，只留 P0——核心循环还能从产出走到反哺起点吗？能，则 P0 集合正确；不能，则有系统被错标。

**优先级与依赖一致**：被依赖的系统优先级不能低于依赖它的系统（资源入口型系统必为 P0；消费型/增益型系统可后置）。

## 在问答中如何用（systems_resources 节点）

实测 systems_resources 是 question → checkpoint 的交互节点。harness 用本卡（配合 resource-economy 卡）：

1. **先列系统清单**。基于已确认的核心循环/差异化锚点，问"要支撑这个循环，需要哪几个系统？"给推荐清单（呼应 genre_scope 已定的核心系统数，如 5~7 个），option_id:0 增删。
2. **逐系统写说明书**。对每个系统连续追问：它干什么（目标）/玩家做什么（机制）/首版做多少（MVP 量）/它的产出消耗连到谁（主循环关系）。
3. **强制标优先级**。对每个系统问/判"它是 P0/P1/P2？"——用"砍了它循环还闭合吗"和"它是不是差异化核心/资源主入口"来定级，给理由。
4. **跑 MVP 闭合检查**：把 P0 系统连成一圈，确认核心正反馈链闭合；若不闭合，提示某个被错标为 P1/P2 的系统其实是 P0。
5. **生成系统设计卡（按 P0/P1/P2 分组的系统说明书）作为检查点**。

收敛判据：每系统有完整说明书 + P0/P1/P2 标注 + P0 集合满足 MVP 闭合 + 优先级与依赖一致 → 出检查点。

之后进入 resource-economy（定资源流）与 numeric_skeleton（落数值）。

## 反模式/坑

- **只列系统不分级**：所有系统平级 → 不知道先做什么、首版投入失控。每个系统必标 P0/P1/P2。
- **P0 标太多**：把 5+ 系统都标 P0 → 原型阶段做不完、验证不聚焦。P0 应是"缺了循环就断"的最小集合（通常 2~4 个）。
- **差异化系统没标 P0**：项目的差异化核心被排到 P1/P2 → 最该早验证的东西最后做。差异化锚点对应的系统必须 P0。
- **资源入口系统后置**：产出主资源的系统标成 P1 → 依赖它的系统无法验证。资源主入口必为 P0。
- **系统说明书缺"与主循环关系"**：只写机制不写它怎么连进循环 → 无法判断优先级、容易做出孤岛系统。每个系统必须说清产出/消耗流向。
- **P2 直接砍成 0**：把增益系统完全砍掉而非轻量化 → 可能丢失构筑深度/差异化。P2 应"首版轻量"而非删除（见 scope-discipline）。
