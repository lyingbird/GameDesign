# 6. systems_resources — 系统模块

## 目标 (what to lock down)
把核心循环落成可实现的系统清单与资源经济：
- **首版系统清单**（哪些系统模块进首版，预置几个互斥"套餐"如六系统闭环版/极简原型版/经营强化版/内容扩张版）
- **系统优先级**（P0 核心验证 / P1 主循环扩展 / P2 构筑加深，避免所有系统一起抢资源）
- **主资源流结构**（几种主资源、各自的产出 Faucet 与消耗 Sink，保证资源流闭合）
- **首版减法**（主动延期/砍掉哪些系统，给核心留打磨空间）

本节点同时喂 GDD §6 系统设计 与 §7 资源经济两章。

## 子维度提问顺序 (ordered sub-dimensions)
固定四问：
1. **首版系统清单**（选一个系统套餐）。
2. **系统优先级排序**（P0/P1/P2 分层）。
3. **主资源流结构**（单资源/三主资源闭环/多资源细分/金币经营流）。
4. **首版减法**（延期/砍掉哪些，给出最不该砍的提醒）。

## 好问题模板 (推荐项 + 论证)
示例（资源流，引用优先级 + 挂机品类通病）：
> **Q：** 主要资源流采用哪种结构？
> **MSG：** 优先级已锁定为「禁书与研读优先」，现在要定资源流：哪些资源负责产出，哪些负责消耗，避免挂机游戏最常见的"资源堆满但没地方花"。
> 我建议选**「三主资源闭环」**。理由是它把主循环拆得最清楚：**知识碎片**支撑日常研读与馆区修复，**禁书钥印**控制中期系统质变，**灵墨**承接技能与装备构筑。这样 P0 可以先跑通知识与钥印，P1/P2 再接入灵墨。如果选「单资源极简」，后期禁书、馆区、技能都会抢同一种资源，数值容易失控；「多资源细分」内容量和 UI 会膨胀；「金币经营流」会把重心拉向店铺经营，不利差异化。
> **选项：**
> [1] 三主资源闭环：知识碎片用于修复与点亮；禁书钥印用于禁书解读；灵墨用于技能强化与装备铭刻（推荐）
> [2] 单资源极简：所有研读、修复、研究、升级围绕知识碎片一种主资源
> [3] 多资源细分：按馆区拆分奥术/历史/炼金/星象等多类知识
> [4] 金币经营流：研读产知识，订单产金币，金币买修复/装备/材料
> [0] 其他/自定义（请在 text 字段填写自由描述）

模板规则：系统清单论证须保证套餐"刚好覆盖主循环、不撑爆 Scope"；优先级论证须把 P0 钉在差异化骨架上（"差异化不是有很多系统，而是 X 改写规则"）；资源流论证须给每种资源标清 Faucet/Sink，并点名挂机品类通病（资源堆满没处花）；减法论证须明确"最不该砍的是哪个、为什么"。

## 收敛判据 (when to emit checkpoint)
系统清单 / 优先级 / 资源流 / 减法四项确认后，发系统范围确认卡。

## 检查点确认卡 (确认卡)
标题：**「系统范围确认」**。preview 三块：
> **系统列表**：六系统闭环版——研读派遣 / 禁书研究 / 离线收益 / 馆区修复 / 技能成长 / 装备构筑（每条带一句职责）。
> **系统优先级**：P0 研读派遣·禁书研究·离线收益；P1 馆区修复·技能成长；P2 装备构筑。
> **资源流闭合性**：三主资源闭环——知识碎片 / 禁书钥印 / 灵墨，逐一列产出来源与消耗去向。

决策选项：
- [1] 同意继续（默认）
- [2] 系统太多，需要裁剪
- [3] 资源流不闭合，重设计
- [0] 其他/自定义重做方案（请在 text 字段填写）

## 局部回炉规则
- 选 [2] **系统太多，需要裁剪** → 只重问系统清单/优先级（推更精简的套餐），**保留资源流之外的上游**。
- 选 [3] **资源流不闭合，重设计** → 只重问资源流结构这一维度，保留系统清单与优先级，重新校验每种资源的 Faucet/Sink 闭合。
- 选 [0] → 按 text 自定义调整。

## 产出 (designContext keys → GDD sections)
设置 `designContext`：`systems`（系统列表+职责）、`system_priority`（P0/P1/P2 分层）、`resource_flows`（主资源+Faucet/Sink+闭合结论）、`cut_list`（首版延期/砍掉项）。
喂给 GDD **§6 系统设计**（按 P0/P1/P2 分系统）与 **§7 资源经济**（主资源/源汇关系/产出消耗节奏/闭环验证）。
